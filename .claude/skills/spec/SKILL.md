# spec: 사양서 작성·갱신

코드로 구현한 동작은 반드시 사양서에 남는다. 코드와 사양서가 어긋난 PR은 미완성이다.

## 절차

1. 변경이 **동작**을 바꾸는지 판단한다.
   - 안 바꿈(리팩터링·이름 변경·테스트 추가만) → 사양서 갱신 생략, PR에 "동작 변경 없음" 명시. 끝.
2. 대상 파일 결정
   - 기존 기능의 변경 → `docs/specs/`의 해당 파일을 **직접 수정** (사양서는 최신 상태를 유지하는 문서. intent-log와 달리 덮어써도 된다).
   - 새 기능 → `docs/specs/<기능>.md` 새로 작성.
3. 아래 항목을 채운다. 해당 없는 항목은 지운다.
4. 코드와 대조한다: 사양서에 적은 숫자·경계값·분기마다 해당 코드 또는 테스트가 있는지 확인. 테스트가 없는 규칙은 "테스트 없음"이라고 적거나 테스트를 추가한다.
5. 상단 메타의 `상태`와 intent-log 링크를 갱신한다.

## 템플릿

```markdown
# <기능> 사양

- 상태: 초안 / 구현 중 / 구현 완료 (vX.Y.Z)
- 의도 기록: [`intent-log/<file>.md`](../intent-log/<file>.md)

## 1. 목적
## 2. 범위 밖 (이번에 하지 않은 것)
## 3. 흐름 / 상태
(상태 머신, 화면 전이. 표나 다이어그램)
## 4. 규칙
(숫자·경계값·우선순위까지 구체적으로. "적당히" 금지)
## 5. 저장 데이터
(localStorage 키, 형식, 마이그레이션)
## 6. 테스트
(규칙 ↔ 테스트 대응)
## 변경 이력
| 날짜 | PR | 내용 |
```

## 원칙

- "무엇을 어떻게 동작시키는가"를 쓴다. "왜"는 intent-log 몫이니 링크만 건다.
- 에이전트가 임의로 정한 값도 사양서에는 그대로 적되, intent-log의 "에이전트가 정한 것" 표에도 있어야 한다.
