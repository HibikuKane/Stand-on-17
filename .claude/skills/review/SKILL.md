# review: PR 리뷰

코드만 보지 말고 **사용자 의도 대비** 구현을 본다.

## 절차

1. PR 본문 확인
   - 작성자 표기(첫 줄)가 있는가. 없으면 지적 (`nit`).
   - 목적 / 변경 범위 / 사양 / 에이전트 판단 / 검증 섹션이 채워졌는가.
2. 맥락 읽기: PR이 링크한 `docs/intent-log/`와 `docs/specs/`를 먼저 읽는다.
3. 범위 확인: 실제 diff가 "변경 범위"와 일치하는가. 선언하지 않은 변경이 섞였으면 지적.
4. 정합성: 코드 ↔ 사양서 ↔ intent-log가 서로 맞는가. 동작이 바뀌었는데 사양서가 그대로면 지적.
5. 정확성: 룰·정산·상태 전이 버그를 찾는다. 가능하면 `npm test`, `npm run build`를 돌리고, 의심 가는 경로는 테스트를 임시로 써서 재현한다.
6. 에이전트 판단 검토: 근거가 약한 가정은 지적하되 "결정은 사용자"라고 명시한다.
7. "범위 밖" 처리
   - 범위 밖의 신규 기능·이번 diff와 무관한 기존 문제 → 지적하지 않고 후속 제안으로만.
   - 이번 diff가 유발한 회귀·기존 사양 위반·기능 완성에 필수인 누락 → 범위 선언과 관계없이 지적한다.

## 출력 형식

첫 줄 작성자 표기 후, 심각도 순으로:

```
> 🤖 작성: Claude (Claude Code)

## 요약
<한두 줄. 머지 가능 / 수정 필요>

## 지적
### [P1] <한 줄 요약>
- 위치: `src/engine/game.ts:123`
- 재현: <입력/조작> → 기대: <값> / 실제: <값>
- 제안: <수정 방향>

## 사양·의도 정합성
<불일치 목록 또는 "문제 없음">

## 에이전트 판단에 대한 의견
<사용자가 결정할 항목>
```

심각도: `P0` 데이터 손실·크래시 / `P1` 룰·정산 오류 / `P2` 엣지 케이스·UX 버그 / `nit` 스타일·문서.
재현하지 못한 지적은 "추측"이라고 표시한다.
